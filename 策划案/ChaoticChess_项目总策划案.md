## 2. 项目概述

### 2.1 一句话定位

**本地双人热座 3D 六边形战棋**。核心是**有限行动点 + 元素反应 + 棋盘可被道具实时改造 + 城邦差异化对局**——棋盘不是固定舞台，而是玩家可以动手改造的资源。

### 2.2 Fun Hypothesis（第一乐趣来源）

> **好玩的核心是：在一个被元素反应和棋盘改造不断搅动的战场上，用有限的行动点做出"这一步会不会翻盘"的判断。**

检验标准：如果删掉**元素反应**或**棋盘改造**中的任意一项，游戏就退化成"两拨棋子在六边形上对撞"——那样它还是同一个游戏吗？**不是**。这两条是特色支柱，其余系统服务于它们。

### 2.3 品类 / 平台 / 受众 / 单局时长

| 维度 | 结论 | 备注 |
|---|---|---|
| **品类** | 回合制战棋（Tactics / SRPG 变体） | 无格子升级线，单局制 |
| **平台** | PC（Windows），Unity 6 LTS + URP | 局域网联机为**远期目标**，架构已预留 |
| **目标用户** | 战棋爱好者；本地同屏双人对战 | 非联网、非移动端优先 |
| **单局时长** | 目标 **20~40 分钟** | **[PLACEHOLDER]** 未经实测；若实测 >40 分钟则需缩短回合数或提高伤害效率 |
| **人数** | 2 人（P1 / P2），本地热座 | 联机时仍为 1v1 |

### 2.4 Design Pillars（四条不可妥协的体验标准）

| # | 支柱 | 含义 | 用来否决什么 |
|---|---|---|---|
| **P1** | **空间是资源，不是背景** | 棋盘可增删、可改造、格子有元素/增益效果；站位与地形是决策的一部分 | 否决"棋盘固定不变""无地形交互"的设计 |
| **P2** | **反应链可预期、结果可复现** | 元素反应用**整数元素量**结算，同输入必得同输出；便于复盘与平衡调试 | 否决概率性元素结算、模糊的"随机增益" |
| **P3** | **信息透明** | 伤害区间、范围高亮、元素附着、跳字反馈全部可见——玩家输要输得明白 | 否决隐藏数值、暗改概率、不可见的地雷机制 |
| **P4** | **节奏优先于表演** | 单次表现（动作/特效）时长受预算约束（≤0.3 秒级），演出不得吞掉对局节奏 | 否决不可跳过的长演出、拖慢回合的表现 |

## 3. 核心玩法循环

### 3.1 三层循环

| 层 | 时长 | 循环内容 | 玩家动机 |
|---|---|---|---|
| **Moment-to-moment** | 0~30 秒 | 选中棋子 → 查看移动/攻击范围 → 移动 → 攻击/放技能 → 观察跳字与反应 → 结束行动 | "这一步能不能多打一点、多赚一点金币" |
| **Session** | 5~30 分钟 | 选棋 → 部署 → 回合行动 → 金币结算 → 买装备/道具 → 胜负判定 | "我这套棋子+装备在本局城邦下能不能滚成雪球" |
| **Long-term** | 跨局 | 累计局外金币 → 购买棋子解锁棋池 → 解锁更大的每方棋子数 → 尝试更多组合 | "凑齐棋子池，试不同的阵容组合" |

### 3.2 一局完整流程

```
大厅（对局配置 + 城邦排除选择）
      ↓  开始游戏（= 提交并开局）
局内：选棋子（双方各 N 个）→ 部署 → 回合行动（含商店/背包/道具）
      ↓
胜负判定 → 结算（反馈 + 局外金币）
      ↓
返回大厅 / 重开一局
```

## 4. 关键设计决策（已拍板，长期有效）

这些是项目中最容易"被后来者改错"的决定，**改动前需回到本文档确认**。

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **全局被动 = 在场即生效**，死亡后失效 | 让"保护核心棋子"有战略意义（如复活、回能类被动） |
| **D2** | **甘雨：蓄力完全替代能量**（无能量条，蓄力层数 0~3 驱动大招） | 角色差异化——用另一套资源模型表达"狙击手"定位 |
| **D3** | **"横向 3 格" = 环切线 3 格**（目标格 + 同环左右邻居） | 六边形棋盘上"横"没有直觉定义，环切线是唯一几何自洽的解释 |
| **D4** | **嘲讽 = 强制锁定**（傀儡在场时，敌方本回合只能攻击傀儡） | 不做"仇恨值/概率吸引"，避免引入隐性数值 |
| **D5** | **范围配置内联进 PieceData**（砍掉独立 SO 层） | 避免资产爆炸；`RangeProviderFactory` 按类名实例化，保留可插拔性 |
| **D6** | **伤害类型三分类 × 元素附着 是正交维度** | 物理伤害也可以带元素（如克洛琳德路径伤害 = 物理类型 + 雷元素），不可混为一谈 |
| **D7** | **唯一被动去重仅作用于装备被动** | 角色被动是出厂配置不重复；复用装备被动模板是合理 DRY |

### 4.1 伤害类型与防御的关系

| 伤害类型 | 受防御减伤 | 受护盾拦截 | 触发反甲 |
|---|---|---|---|
| **物理** Physical | ✓ | ✓ | ✓ |
| **魔法** Magical | ✗ | ✓ | ✗ |
| **真实** True | ✗ | ✗ | ✗ |

### 4.2 元素附着规则

**默认**：角色造成的**任何直接伤害**（普攻 / 大招 / 被动）默认**带元素**（附着角色先天元素、可触发反应）。
**例外**（不附着）：反伤、感电 DoT、超载爆炸等**非"角色主动直接伤害"**。
**实现约束**：每个直接伤害效果类带一个「是否附着元素」的配置参数（默认 true）。

### 5.2 系统交互要点（易打架的地方）

| 交互对 | 关系 | 说明 |
|---|---|---|
| 元素反应 × 伤害类型 | **正交** | 反应倍率作用于伤害，不改变伤害类型 |
| 棋盘改造 × 寻路 | intended | 增删地块后需重算连通性与路径 |
| 城邦机制 × 战斗结算 | 需过滤 | 非本局城邦的机制必须**不生效**（`XxxManager.XxxActive` 内聚判定） |

| 元素格 × DoT 跳字 | **分级** | 环境伤害用轻量受击表现，避免每回合全场抖动 |

## 7. 配置与数据流

```
策划配置        配置表（Excel）              游戏数据
────────      ──────────────           ──────────
全局参数   →   全局参数配置表.xlsx   →    GameConfig.asset 等 SO
棋子/被动  →   棋子/被动效果生成器   →    PieceData / jsonParams
装备/道具  →   装备/道具配置生成器   →    EquipmentData.asset（回写脚本）
                                  ↓
                          运行时读 SO → MVC 各层
```

**约定**：
- 配置表统一放 `配置表\`（含 `tools\` 回写脚本，支持 `--dry-run`）
- **全局平衡参数只放 `GameConfig`**；城邦参数放各自 `CityState/<城邦>/Model/*Config.cs`
- 新建配置资产时，`CreateAssetMenu` 必须指定**无空格的 `fileName`**（否则 `Resources.Load` 静默失效）

## 8. 技术架构摘要

| 层 | 做法 |
|---|---|
| **模式** | MVC 分层；工厂 + 策略（范围 Provider / 被动效果）；ScriptableObject 全数据驱动 |
| **可插拔** | 范围与移动用「Provider 类名 + JSON 参数」配置，新增模板不改棋子代码 |
| **场景** | `MainMenu`（大厅，Build index 0）+ `SampleScene`（局内，1）；**保留直接开局内调试的通道** |
| **表现** | 棋子动作全程序化（DOTween），**无动画文件依赖**；视觉反馈走 MPB 颜色通道 |
| **联机预留** | 账号走 `IAuthProvider`；选择/结算入口单一且参数化；对局状态存非 UI 载体 |

## 10. 本文档的使用方式

- **改动任何已实现系统前** → 先读第 4 节（关键决策），确认不是在推翻一个有意为之的设计
- **接手某个系统** → 读本文档第 5 节找到分册，分册含字段定义表、边界状态与配置路径
- **调整数值** → 读第 6 节 + `配置表\全局参数配置表.xlsx`，不要在代码里改魔数
