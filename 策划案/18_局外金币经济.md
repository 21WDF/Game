## 2. 系统概述

### 2.1 目的

给玩家一个**跨局的理由**——"**再打一局**"。

局内金币随对局结束归零，局外金币**跨局累积**，用于解锁棋子。这是本项目的**长期钩子（Long-term loop）**。

### 2.2 玩家体验目标

| 目标 | 具体表现 |
|---|---|
| **每局都有收获** | 即使打输了也有金币进账（失败 +100）→ 不会因为连败而完全没有进展 |
| **里程碑清晰** | 攒够 500 就能买一个新棋子，且**解锁后立即能用** |
| **解锁有实感** | 买到第 5 个棋子后，"每方 5 个"选项从置灰变可选 |

### 2.3 在整体中的位置

```
局内对战（胜负）
      ↓
局外金币（本册）— 跨局累积
      ↓
棋子商店（消耗）→ 棋池扩大 → 解锁更大的「每方棋子数」选项 → 影响下一局
```

## 3. 核心规则

### 3.1 ⭐ Sources（产出）

| 来源 | 金额 | 时机 |
|---|---|---|
| **参与奖** | **+100** | 每局结束（无论胜负） |
| **胜利奖** | **额外 +200** | 胜利时 |
| **单局合计** | **败 100 / 胜 300** | |

**设计判断**：**失败也有 100**——保证连败的玩家仍在推进（否则"输了等于白打"会迅速劝退）。

### 3.2 ⭐ Sink（消耗）

| 消耗 | 金额 |
|---|---|
| **购买棋子** | **500 / 个** |

**当前金币的唯一出口就是购买棋子。**

### 3.3 ⭐ 唯一发币点与幂等

```csharp
int SettleGameOutcome(bool localPlayerWon)
```

| 要点 | 说明 |
|---|---|
| **唯一发币点** | 结算只在这一处（便于将来"各自胜负"分别结算） |
| **幂等** | 静态标志 `_currentGameSettled` + `BeginNewGame()` 重置 |
| **重置时机** | `GameFlowController.Start` 每次进局内场景调用 → 重开一局（重载场景）后会重新置位，**新局可正常结算** |
| **防重复** | `UI_GameOver` 可能被重复触发（含 Forfeit / 多订阅）→ 靠幂等标志跳过 |

> **为什么幂等是必需的**：`UI_GameOver` 面板有"重开一局"按钮，若结算挂在面板显示逻辑上又没有保护，**玩家反复点就能刷金币**。

### 3.4 ⭐ 结算归属参数化（联机预留）

```
SettleGameOutcome(bool localPlayerWon)
```

**由调用方决定"本机是否获胜"**：

| 模式 | 调用方传入 |
|---|---|
| **本地热座** | `winner == PlayerSide.P1`（本机视角 = P1） |
| **联机** | `winner == 我的阵营` |

> **这条改动的意义**：早期设计是"固定按 P1 判定"。那在**联机时本机可能是 P2** → 赢了也拿不到奖励 → **必须改逻辑**。
> 改成参数化后，**联机时只改调用方一处，结算逻辑与 UI 零改动**——这才是"预留"该有的样子。

### 3.5 ⭐ 棋池解锁联动

**解锁判据**：`拥有棋子数 ≥ 选项目标值`

| 拥有数 | 可选「每方棋子数」 |
|---|---|
| 4（初始） | 仅 **3** |
| 5 | 3 · **5** |
| 7+ | 3 · 5 · **7** |

**选择"大于等于"的理由**：每方要从池子里选 N 个不同的棋子 → **池子必须装得下要选的数**。

**三处钳制**（防"选了 7 但只有 4 个棋子"）：

| 位置 | 作用 |
|---|---|
| 大厅回显 | `Start` 时钳制记录值 |
| 开始前 | `OnStartClicked` 再次钳制 |
| 选棋子界面 | `Show()` 防御性钳制 |

## 4. 数值与公式

### 4.1 ⭐ 经济表（核心）

```
Sources：
  败局  +100
  胜局  +300（100 参与奖 + 200 胜利奖）
  50% 胜率下均值 = (100 + 300) / 2 = 200 / 局

Sink：
  棋子 500 / 个

待解锁棋子数 = 9（可上场棋子） - 4（初始） = 5 个
全解锁成本 = 5 × 500 = 2500 金币
全解锁需 ≈ 2500 / 200 = 12.5 局
```

**[PLACEHOLDER]**：以上节奏**未经 playtest**。若单局 20~40 分钟，12.5 局约 **4~8 小时**集齐。

### 4.2 ⚠️ 通胀风险评估（本系统最大的设计问题）

**问题：金币的 sink 只有一个（买棋子），且总量有限。**

```
金币总需求 = 2500（买完 5 个待解锁棋子）
之后呢？
  → 9 个棋子全部拥有后，金币再无用途
  → 但每局仍在产出（+100 / +300）
  → 金币只增不减，变成无意义的数字
```

**这属于典型的"source 找不到对应的 sink"**（设计原则：任何 source 没有 sink，通胀只是时间问题）。

**可用解法**（供参考，需你选）：

| 方案 | 说明 |
|---|---|
| **A. 增加 sink** | 让金币有第二个用途（如"重掷城邦"、"开局购买装备"、"棋子皮肤"） |
| **B. 提高单价 / 增加棋子** | 延长解锁线（治标，最终仍会买完） |
| **C. 让金币可转局内** | 局外金币在开局时兑换成局内初始金币（**直接把两个经济系统打通**） |
| **D. 接受上限** | 承认"集齐即毕业"，把金币定位为一次性成长线（**最简单，但要明确这是设计意图**） |

> **我的倾向**：**C 最有意思**——它让"攒金币"这件事在**每一局**都有意义，而不只是前 12 局。但它会打通两个经济系统，需要重新评估局内金币的平衡（见《回合与资源》§4.2 与《商店》D17）。

### 4.3 收益曲线的特性

**当前设计：收益固定**（不随表现变化）

| 优点 | 缺点 |
|---|---|
| 可预期、无挫败感 | **无"越玩越赚"的动力**（高手与菜鸟收益相同） |
| 简单，不需要额外平衡 | 长期动机偏弱（只有"攒够 500"这一个里程碑） |

> **这是一个有意的简化**。若将来想加强长期动机，可考虑"按表现加成"（如击杀数、剩余 HP），但那会引入新的平衡面。

## 5. 数据结构（字段定义表）

### 5.1 `PlayerProfileConfig` 中与本系统相关的字段

| 字段（示意） | 默认 | 说明 |
|---|---|---|
| 每局收益 | **100** | 参与奖 |

| `initialPieceIds` | 菲林斯/杜林/哥伦比亚/克洛琳德 | 可改 |

> **全部在 ScriptableObject 里** → 调参改资产即可，不碰代码。

### 5.2 `PlayerProfileService` 相关 API

| 成员 | 签名 | 说明 |
|---|---|---|
| `SettleGameOutcome` | `int (bool localPlayerWon)` | **唯一发币点**，返回本局所得 |
| `BeginNewGame` | `void` | 重置幂等标志 |
| `GetOwnedPieces` | `List<PieceData>` | 棋池（过滤召唤物） |
| `GetValidPieceCount` | `int (int requested)` | 钳制到已解锁范围 |
| （购买入口） | — | 由 `UI_PieceShopPanel` 调用服务层 |
| （内部标志） | `static bool _currentGameSettled` | 幂等保护 |

### 5.3 `UI_PieceShopPanel`

| 职责 | 说明 |
|---|---|
| 展示 | 金币余额 + 全部棋子列表（已拥有 / 未拥有 + 价格） |
| 购买 | 金币足够 → 扣款 + 解锁 + 即时写盘；不足 → 拒绝并提示 |
| 刷新 | 购买后**立即刷新**「每方棋子数」的解锁状态 |

## 7. 边界与失败状态

| 场景 | 期望行为 | 状态 |
|---|---|---|
| 同一局重复结算 | **幂等**（静态标志跳过） | ✓ |
| 重开一局 | `BeginNewGame()` 重置 → 新局可结算 | ✓ |
| 返回大厅再开局 | 同上 | ✓ |
| 金币不足购买 | 拒绝 + **不扣款** | ✓ |
| 购买后解锁状态 | **立即刷新**（5 可能刚可用） | ✓ |
| 金币变更 | 即时写盘 | ✓ |
| 棋池过滤 | `GetOwnedPieces` **已排除召唤物** | ✓ |
| 选项目标值 > 拥有数 | 三处钳制回退 | ✓ |
| **9 个棋子全部拥有后** | ⚠️ **金币无处可花**（见 §4.2 通胀风险） | ⚠️ |
| 联机时各自身份 | `localPlayerWon` 由调用方决定 | ✅（预留） |

## 10. 待确认项

1. ⚠️ **通胀风险（本系统最大问题）**：**金币只有一个 sink（买棋子），买完 9 个就无处可花**，而每局仍在产出 → 需要增加 sink 或明确"集齐即毕业"。**建议优先决策**（§4.2 列了 4 个方案，我倾向"金币可转局内初始金币"）
2. **12.5 局全解锁的节奏是否合适**（§4.1）：[PLACEHOLDER]，需 playtest
3. **胜负收益差（200）是否足够**：败 100 / 胜 300 的差距是否形成"想赢"的动力
4. **是否需要"按表现加成"**：当前收益固定，长期动机偏弱（§4.3）
5. **实机验证**：首次启动金币是否为 0、打一局后是否正确 +100/+300、买棋子后选项是否解锁
6. **结算金币反馈**：`UI_GameOver.rewardText` 是否已接线（让玩家知道"这局赚了多少"）
7. **多账号金币独立性**：各账号金币应完全独立——需实测
8. **局外经济是否需要配置表**：目前参数在 SO 里，未纳入 `配置表\`
