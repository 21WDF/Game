## 2. 系统概述

### 2.1 目的

让**"用什么打什么"**和**"打几下"**产生组合意义——不是简单的属性克制，而是**元素量（Gauge）的整数消耗博弈**。

回答的问题：**"我现在附着什么元素、还剩多少量、下一击会不会触发反应、触发后还剩下什么"**。

### 2.2 玩家体验目标

| 目标 | 具体表现 |
|---|---|
| **可预期** | 用**整数**结算，同样的输入必得同样的输出——玩家能复盘"为什么这次触发了蒸发" |
| **有积累感** | 元素附着不是"打一下就上"，而是**有量（Gauge）**——连打同元素会叠加 |
| **克制有感知** | 水打火、火打冰时，**消耗更少**（克制方消耗减半）→ 更容易打出反应 |

### 2.3 在整体中的位置

```
攻击力 / 防御力
      ↓
伤害计算（消费反应的 DamageMultiplier / ExtraDamage）
      ↑ 提供反应参数
元素反应（本册）— 附着 / Gauge 消耗 / 6 种反应效果
      ↓
跳字反馈 · 元素光环 · 元素格 · 城邦机制（元素城邦）
```

## 3. 核心规则

### 3.1 四元素

| 元素 | 中文 | 备注 |
|---|---|---|
| `Fire` | 火 | 克冰 |
| `Water` | 水 | 克火 |
| `Thunder` | 雷 | **不参与克制** |
| `Ice` | 冰 | 被火克 |

### 3.2 ⚠️ 城邦过滤：元素系统只在「元素城邦」生效

```csharp
if (!ElementSystemActive) return (ElementType.None, 0);
```

`ElementReactionTable.ElementSystemActive` 转发自 `ElementCityManager.ElementSystemActive`（**单一入口**）。

**效果**：非元素城邦下——
- **不附着**元素（所有附着写入点写 None）
- **不消耗**（Gauge 保持 0）
- **不触发反应**

> **这是"机制按城邦过滤"的落地**：元素系统是**元素城邦的专属机制**，不是全局玩法。判定收敛在 `ElementCityManager` 一处，`PieceModel` 与 `ElementReactionTable` 只做转发。

### 3.3 元素附着与 Gauge

| 规则 | 值 | 说明 |
|---|---|---|
| 普攻附着量 | **1** | `triggerGauge` |
| 大招附着量 | **2** | `triggerGauge`（双倍） |
| 附着上限 | `PieceModel.MaxElementGauge` | ⚠️ 具体值待核（见 §10） |
| 同种元素 | **叠加**（带上限） | 不触发反应 |
| 默认附着 | 角色造成的**任何直接伤害**默认带元素 | 例外见 §3.6 |

### 3.4 克制表（单向）

```
水 → 克 火
火 → 克 冰
雷 → 不参与克制
```

**克制的作用**（重要，容易误解）：

| 克制影响 | 克制**不**影响 |
|---|---|
| ✓ 反应**消耗量**（克制方有效值 ×2、实际消耗 ÷2） | ✗ **伤害倍率**（倍率只看反应类型） |

> **一句话**：克制让你**更容易打出反应**（省元素量），但**不会让这一击打得更疼**。

### 3.5 Gauge 消耗算法（六步，纯整数）

**触发条件**：底元素与触发元素**不同**且底元素 Gauge > 0。

```
a. baseEff = baseGauge;  trigEff = triggerGauge
b. 触发方克底方 → trigEff ×= 2
   底方克触发方 → baseEff ×= 2
c. consume = min(baseEff, trigEff)              ← 有效消耗量
d. 底方克触发方 → baseConsumed = max(consume/2, 1), trigConsumed = consume
   触发方克底方 → baseConsumed = consume, trigConsumed = max(consume/2, 1)…（见下注）
   无克制       → baseConsumed = trigConsumed = consume
e. baseGauge -= baseConsumed;  triggerGauge -= trigConsumed
f. baseGauge > 0 → 保留底元素；triggerGauge > 0 → 附着变为触发元素；都 ≤0 → 清除
```

> **注**：源码中"触发方克底方"分支为 `baseConsumed = consume; trigConsumed = consume / 2`（**没有** `max(...,1)` 保底）；只有"底方克触发方"分支有 `max(consume/2, 1)` 保底。**这是一处不对称**，见 §10 待确认项。

**三种输入情况**（算法的前置分支）：

| 情况 | 条件 | 结果 |
|---|---|---|
| 1. 无底元素 | `baseGauge ≤ 0` 或 `baseElement == None` | 直接附着触发元素，Gauge = `triggerGauge` |
| 2. 同种元素 | `baseElement == triggerElement` | **叠加**：`min(baseGauge + triggerGauge, MaxElementGauge)` |
| 3. 不同元素 | 其他 | **走上面的六步消耗算法** |

> **步骤 6 的数学保证**（源码注释）：**不可能出现双方都 > 0 的剩余**。因为 `consume = min(baseEff, trigEff)`——至少有一方的有效值 ≤ consume，被扣光。

### 3.6 元素附着默认规则

**默认**：角色造成的**任何直接伤害**（普攻 / 大招 / 被动）**默认带元素**（附着角色先天元素、可触发反应）。

**例外**（不附着）：
- 反伤
- 感电 DoT
- 超载爆炸
- 其他**非"角色主动直接伤害"**

**实现约束**：每个直接伤害效果类带一个「是否附着元素」的配置参数（默认 true，false 保持不附着）。

## 4. 数值与公式

### 4.1 演算示例（四个，覆盖全部算法分支）

**例 1 · 无克制（火底 + 雷触发）**

```
底：火 gauge 1 ；触发：雷 gauge 1
b. 雷不参与克制 → baseEff = 1, trigEff = 1
c. consume = min(1, 1) = 1
d. 无克制 → baseConsumed = 1, trigConsumed = 1
e. 火 1-1 = 0 ；雷 1-1 = 0
f. 都 ≤ 0 → 清除 → (None, 0)
```
> **结果**：元素被**完全消耗**，不残留。

**例 2 · 触发方克底方（火底 + 水触发）** ⭐

```
底：火 gauge 3 ；触发：水 gauge 1
b. IsCountered(触发=水, 底=火) ✓ → trigEff = 1 × 2 = 2
   baseEff = 3
c. consume = min(3, 2) = 2
d. 触发方克底方 → baseConsumed = 2, trigConsumed = 2/2 = 1
e. 火 3-2 = 1 ；水 1-1 = 0
f. 火 > 0 → 保留火，gauge 1
```
> **结果**：**火没被吃光**（剩 1），水全消耗。克制方（水）消耗减半，所以 1 点水就消耗了 2 点火。

**例 3 · 底方克触发方（水底 + 火触发）** ⭐ 展示保底

```
底：水 gauge 2 ；触发：火 gauge 1
b. IsCountered(底=水, 触发=火) ✓ → baseEff = 2 × 2 = 4
   trigEff = 1
c. consume = min(4, 1) = 1
d. 底方克触发方 → baseConsumed = max(1/2, 1) = max(0, 1) = 1   ← 保底生效
                     trigConsumed = 1
e. 水 2-1 = 1 ；火 1-1 = 0
f. 水 > 0 → 保留水，gauge 1
```
> **注意保底**：`1/2` 在整数除法下是 **0**，`max(0,1)` 把它拉回 **1**——否则底元素会"零消耗"保留，反应等于没发生。

**例 4 · 同种元素叠加**

```
底：火 gauge 1 ；触发：火 gauge 1
情况 2 → min(1 + 1, MaxElementGauge) = 2（若上限 ≥ 2）
```
> **不触发反应**，只是量变大。连打同元素是"攒元素"的手段。

### 4.2 六种元素反应

| 反应 | 组合 | 效果（`ReactionConfig` 字段） |
|---|---|---|
| **蒸发** | 水 + 火 | `DamageMultiplier` |
| **融化** | 火 + 冰 | `DamageMultiplier` |
| **超载** | 火 + 雷 | `KnockbackDistance`（击退） |
| **感电** | 水 + 雷 | `DotDamagePerTurn` / `DotTurns`（持续伤害） |
| **冻结** | 水 + 冰 | `FreezeTurns`（无法行动） |
| **超导** | 冰 + 雷 | `DefenseReduction` / `DefenseReductionTurns`（减防） |

> **反应的具体数值在 `ReactionDatabase.asset`**（数据外置），不在代码里——新增一种反应**不需要改代码**。见 §6。

## 5. 数据结构（字段定义表）

### 5.1 `ReactionConfig`（反应配置）

**位置**：`ElementReactionTable` 内嵌结构体/类

| 字段中文名 | 字段英文名 | 类型 | 注释 | 示例 |
|---|---|---|---|---|
| 伤害倍率 | `DamageMultiplier` | float | 乘在 `baseDamage` 上（见《伤害计算》） | 1.5 |
| 是否清除底元素 | `ClearBase` | bool | **本阶段不单独使用**（覆盖即消耗） | — |
| 额外固定伤害 | `ExtraDamage` | int | 倍率**之后**加，不吃倍率 | 0 |
| DoT 每回合伤害 | `DotDamagePerTurn` | int | 感电；由 `TurnManager.TickElementDuration` 结算 | 5 |
| DoT 持续回合 | `DotTurns` | int | 感电 | 2 |
| 防御降低值 | `DefenseReduction` | int | 超导；`AttackPiece` **伤害计算前**预设 | 5 |
| 减防持续回合 | `DefenseReductionTurns` | int | 超导；0 = 仅当次生效 | 2 |
| 冻结回合 | `FreezeTurns` | int | 冻结；`BattleController` 拦截选中 | 1 |
| 击退格数 | `KnockbackDistance` | int | 超载；结算后由 `KnockbackResolver` 处理 | 1 |

## 7. 边界与失败状态

| 场景 | 期望行为 | 状态 |
|---|---|---|
| 非元素城邦 | 不附着、不消耗、不反应（返回 None/0） | ✓ |
| 无触发元素 | 底元素不变 | ✓ |
| 无底元素 | 直接附着 | ✓ |
| 同种元素 | 叠加（带上限） | ✓ |
| 双方 Gauge 都被扣光 | 清除为 None | ✓ |
| 反应后底元素仍 > 0 | 保留底元素 | ✓ |
| 反应后触发元素仍 > 0 | **附着变为触发元素** | ✓ |
| 数学上双方都 > 0 | **不可能**（算法保证） | ✓ |
| 整数除法导致消耗为 0 | 底方克触发方分支有 `max(...,1)` 保底 | ✓ |
| **触发方克底方分支无保底** | ⚠️ 不对称（见 §10） | ⚠️ |

## 10. 待确认项

1. **`MaxElementGauge` 的具体值**：附着上限是多少？（影响"能攒多少元素"）
2. **⚠️ 克制消耗的不对称**（§3.5 注）：源码中
   - 「底方克触发方」→ `baseConsumed = max(consume/2, 1)`（**有保底**）
   - 「触发方克底方」→ `trigConsumed = consume/2`（**无保底**）

   当 `consume = 1` 时，触发方消耗 = `1/2 = 0` → **触发元素不消耗却触发了反应**。**这是有意的还是遗漏？** 需确认。
3. **6 种反应的具体数值**：在 `ReactionDatabase.asset` 里，本文档未逐一列出（如需可补一张"反应数值速查表"）
4. **`ClearBase` 字段的用途**：注释写"本阶段不单独使用（覆盖即消耗）"——是否还有后续计划？
5. **冻结的表现**：被冻结的棋子是否有视觉标识
6. **元素附着上限与"连打同元素"的收益**：是否值得为了攒元素而连续攻击同一目标（需 playtest）
