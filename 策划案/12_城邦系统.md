## 2. 系统概述

### 2.1 目的

让**同一套棋子在不同对局里呈现不同玩法**。

回答的问题：**"这一局的规则和别的局有什么不一样"**。城邦不是阵营、不是角色属性，而是**本局变量**——每局重新抽取。

### 2.2 玩家体验目标

| 目标 | 具体表现 |
|---|---|
| **开局就有变化** | 选完城邦就知道"这局游戏长什么样"，可以据此调整阵容与思路 |
| **城邦可参与** | 双方各自排除不想要的城邦 → 结果由双方共同影响（不是纯随机） |
| **机制真实生效** | 城邦不仅是名字——对应的机制（元素反应、拍卖行等）真的会在对局中起作用 |

### 2.3 在整体中的位置

```
城邦（本册）— 决定本局有哪些机制生效
      ↓
元素反应（仅元素城邦）· 拍卖行/地下交易（仅贸易城邦）· 棋盘扩展/主将（仅战争城邦）· 四季气候（仅季风城邦）
      ↓
商店 · 棋盘 · 棋子属性 · 胜负条件
```

## 3. 核心规则

### 3.1 六个城邦

|---|---|---|---|

| 2 | **季风** | 四季轮转 · 昼夜 · 五种气候（暴雨/暴雪/高温/飓风/雷暴）· 雷电残留 | ✅ **已落地** |
| 3 | **元素** | 元素反应系统 · 元素格 · 护盾染色 | ✅ **已落地** |

| 5 | **欢愉** | 卡牌 / 手牌系统 | ❌ **未实现** |
| 6 | **邪疑** | 卧底 / 棋子归属转换 | ❌ **未实现** |

> **代码佐证**：`CityState/` 下只有 `Trade` / `Monsoon` / `Element` / `War` 四个城邦子目录——**欢愉与邪疑没有对应实现**。
> 选中未实现的城邦时，本局只有"商店城邦装备池变化"，没有专属机制。

### 3.2 城邦选择流程（排除法）

**规则**（决策 D3 的落地）：

```
1. 双方各排除 2 个城邦（而不是"各选 4 个心仪"）
2. 候选集合 = 双方都没排除的城邦
3. 从候选中随机确定 1 个 = 本局城邦
```

**⚠️ 数学等价性**（关键设计判断）：

> 6 个城邦中「选 4 个想要的」与「排除 2 个不想要的」**完全等价**——候选集合都是"双方都没排除的"。
> 因此**规则本身没有改变**，只是 UI 心智从"勾选想要的"变成"划掉不想要的"。
> 底层 `CityStateModel.Resolve` 的交集算法与确定性保证**原样复用**，转换只在 UI 层完成。

**为什么排除法更好用**：面对 6 个陌生城邦，"**我不想要这个**"比"**我想要这四个**"是更轻松的决策——排除法降低了开局前的认知负担。

**时机**：城邦选择在**大厅**完成（属于"开局前配置"），不在局内。「开始游戏」相当于"提交并匹配"。

### 3.3 结算规则（`CityStateModel.Resolve`）

```csharp
static CityStateKind Resolve(p1Choices, p2Choices, roll)
```

| 步骤 | 说明 |
|---|---|
| 1 | 求交集（P2 选择建哈希集 → 遍历 P1 选择去重收录） |
| 2 | 排除 `None`（非法选择） |
| 3 | **按枚举值排序**（保证确定性） |
| 4 | `intersection[roll % count]` 选定 |
| 5 | 空交集返回 `None` |

**设计要点**：

| 要点 | 说明 |
|---|---|
| **纯函数** | 不依赖 UI、**不自己产生随机数**——`roll` 由调用方传入 |
| **单一随机入口** | 随机收敛在 `CityStateManager.ResolveCityState()` 一处（便于将来换成网络权威 seed） |
| **确定性** | 相同输入 + 相同 roll = 相同结果（排序保证） |
| **单元可测** | 纯函数可脱离 Unity 测试 |

### 3.4 ⚠️ 机制过滤范式（本系统最重要的设计）

**每个城邦机制都有一个静态的"是否生效"开关**，所有相关代码首行判断：

| 城邦 | 过滤入口（静态属性） | 使用者 |
|---|---|---|
| 贸易 | `TradeCityManager.TradeActive` | `TradeCityManager` + **`AuctionManager`** + **`UndergroundTradeManager`**（三者共用） |
| 季风 | `MonsoonManager.MonsoonActive` | `MonsoonManager` |
| 元素 | `ElementCityManager.ElementSystemActive` | `ElementReactionTable` + `ElementTileManager` + `PieceModel` |
| 元素（二级） | `ElementCityManager.DyeingActive` | 护盾染色（= `ElementSystemActive && ShieldDyeingEnabled`） |
| 战争 | `WarCityManager.WarActive` | `WarCityManager` |

**统一的写法**：

```csharp
private static bool XxxActive => /* 当前城邦 == Xxx （+ master 开关） */;
public void SomeMethod() { if (!XxxActive) return; /* 原逻辑 */ }
```

> **这个范式的价值**：城邦机制**不需要在外部到处判断"现在是不是某个城邦"**——判定收敛在各自的 Manager 里，外部代码只管调用，非对应城邦时自动空转。
>
> **这也是"机制按城邦过滤"能可靠落地的前提**——否则每加一个城邦机制，就要在所有调用点加一层判断。

**元素的二级开关**（`ElementSystemActive` → `DyeingActive`）值得单独看：护盾染色需要**两个条件同时满足**（元素城邦 **且** master 开关打开），做成两级查询让调用方不用关心组合逻辑。

## 4. 数值与公式

### 4.1 城邦确定概率

```
6 个城邦，双方各排除 2 个：
  若双方排除互不重叠 → 候选 = 6 - 4 = 2 个 → 每局城邦是这 2 个之一（各 50%）
  若双方排除有 1 个重叠 → 候选 = 6 - 3 = 3 个
  若双方排除完全重叠   → 候选 = 6 - 2 = 4 个

候选数范围：2 ~ 4（鸽笼原理保证 ≥ 2，因为 2+2=4 < 6）
```

> **注意与旧规则的区别**：旧规则（各选 4 个心仪取交集）的候选数**至少 2 个**（2×4=8 > 6 保证交集非空）；新规则（各排除 2 个）的候选数**也是至少 2 个**（6−4=2）。**两者的候选集完全一致**，只是表述相反。

### 4.2 城邦机制的参数

各城邦的机制参数在**各自的 Config 资产**里（见 §5.4），完整数值见 `配置表\全局参数配置表.xlsx` 的 `Monsoon` / `Trade` / `War` sheet。

## 7. 边界与失败状态

| 场景 | 期望行为 | 状态 |
|---|---|---|
| 选中未实现的城邦（欢愉/邪疑） | **不报错**，只是无专属机制（仅商店装备池变化） | ✓（但体验缺失） |
| 无城邦模式 | 跳过选择，本局 `None`，所有机制不生效 | ✓ |
| 非对应城邦访问机制 | `XxxActive` 为 false → 首行 return | ✓ |
| 直接 Play 局内（开发直进） | 本局 `None`（机制全关），正常开局 | ✓ |
| 返回大厅再开局 | 选择状态重置，可重新选 | ✓ |
| 跨局残留 | 各 Manager 的 `OnDestroy` 清单例；战争之城的调换锁定**非战争城邦也清** | ✓ |
| 空交集（理论上不会发生） | `Resolve` 返回 `None` | ✓ |
| 调试指定城邦 vs 大厅结算 | **调试优先**（详见 §10：`DebugManager` 在 0.1s 设置，早于 `BeginPreMatch` 的 0.3s，存在被覆盖的风险——已用"当前城邦非 None 则不覆盖"的思路记录待办） | ⚠️ |

## 10. 待确认项

1. **欢愉与邪疑的机制设计**：这是城邦系统**最大的空缺**。欢愉（卡牌/手牌）是"全新手牌系统"（复杂度二档），邪疑（卧底/棋子归属转换）是三档（**会改动归属与胜负判定，规则歧义最多**）
2. **`ICityStateMechanism` 骨架的启用时机**：接口已定义但只有空实现、无注册路径——二期的接入方式待定
3. **调试城邦被覆盖的风险**：`DebugManager` 在 0.1s 设置城邦，`GameFlowController.BeginPreMatch` 在 0.3s 应用大厅结算 → **从大厅进入时调试指定会被覆盖**（直接 Play 局内不受影响）。修法：写城邦前判断"当前是否已非 None"
4. **城邦机制的视觉表现**：季节/气候/主将等内容是否有对应的视觉呈现
5. **局内是否常驻显示本局城邦**：玩家需要随时知道本局机制是什么
6. **透支机制未按城邦过滤**（见《回合与资源》D5）：`OverdraftFloor` 目前全城邦生效，本应只在贸易城邦可用
7. **`CityStateKind` 枚举的准确命名与值**：本文档按语义列出，需在 `GameEnums.cs` 核对
8. **建议拆分**：本文档是"城邦系统总册"，若需要，可把 4 个已实现城邦各拆一份详规（机制参数、触发时机、边界）
